- [x] TestPuts hardlink race: two hardlinks to the same inode are handled by
  different put clients, which both upload the shared inode file
  concurrently; the second fails with CATALOG_ALREADY_HAS_ITEM_BY_THAT_NAME.
  The test's `waitForStatus("\nStatus: complete")` also matches
  "complete (but with failures".
  - Red: `CGO_ENABLED=1 go test -tags netgo --count 1 -run '^TestPuts$' .`
    (~4.5 min) failed 4/4 runs, including twice on the pre-update deps:

  - Fixed in `server/claims.go` (new), `server/server.go` and
    `server/setdb.go`: when reserving, a hardlink request claims its remote

    abandoned reservation (TTR expiry or retry release) is dropped first.
    Claim errors are logged and the request skipped.

    across clients, including after a client holding both is abandoned.
    `main_test.go` now waits for "\nStatus: complete\n" so failures aren't

- [x] TestSync intermittently fails (seen in `make race-main`,
  main_test.go:3936): waiting for "Uploaded: 1;" on set discoveredSet, it
  shows `Status: complete ... Uploaded: 0; Skipped: 1; ... Orphaned: 1`.
  Passed in the earlier non-race `make test`.
  - Previously ticked as resolved by the test-isolation fix (e4c7b83); that
    was wrong. It's a real server-side race, reproduced at HEAD: in the
    `sync --delete` case, discovery takes the per-set lock first; the removal
    then reads the file's entry (still `uploaded` from the previous run) and
    removes it from iRODS slowly; meanwhile the requeued upload reports
    `orphaned`; then `processDBFileRemoval` calls `UpdateBasedOnRemovedEntry`
    with the stale entry, decrementing `Uploaded`, which discovery had zeroed.
  - Red: `CGO_ENABLED=1 go test -tags netgo --count 1 -timeout 1200s -run
    '^TestSync$' .` repeated: failed 1 of up to 20 runs at HEAD, and 4 of 26
    with the stale-status discovery fix in the working tree.
  - Fixed in `set/db.go`, `set/entries.go` and `server/setdb.go`:
    `RemoveFileEntry` deletes the entry (both buckets) and its failed lookup
    in one transaction and returns the entry as stored, which feeds the inode
    removal and then `UpdateBasedOnRemovedEntry`, still the last step so
    "Removal status" only reaches N/N after all cleanup. Entries record the
    discovery that counted their status (`CountedInDiscovery`), and removal
    only decrements a status the current counts include (an upload result
    this run, or counted by the current discovery).
  - Tests: deterministic server tests forcing the upload-result/removal
    orderings and the cleanup-before-count invariant, and set tests for
    missing and abnormal entries in file and directory sets (still present,
    rediscovered, deleted locally).
