- [x] Possible (reproduce first): `MergeDirs` of a folder under a removed
  folder never returns, so the server request hangs.
  `findAllOtherPathsToExclude` loops until its path equals the stored match,
  but a folder's stored match ends in "/" (`isDirentRemovedFromSet`) and
  `filepath.Dir` never yields that, so the loop climbs past the folder to "/"
  and repeats there forever. Seen as a test hanging at `MergeDirs` for 10
  minutes at 126% CPU. Repro: in a set with folder D, remove D (ToRemove or
  trash) and wait for the removal, then `MergeDirs` D/sub.
  - Source: set-counts-4 late-upload undo cycle 2 (2026-10-22).
  - Reproduced. New `TestServer` leaves "Merging a subfolder of a removed

  - Sibling check: `findChildPathsToExclude` skipped any child whose path

    removal (not in the removed bucket in its own right) was then picked up
    by rediscovery. Red with the hang fixed: the same command exited 1 at
    `Line 3438` with `top/dir/s` in the set's files beside `top/dir/sub/file`
    and `top/kept`. `getChildPathsFromPTrie`, `isDirentRemovedFromSet` and
    `excludeFromRemovedBucket` already normalise the "/".
  - `MergeFiles` doesn't share this path: `putFiles` never touches the
    removed bucket, and exclusions only filter dir walks.
  - Fix (`server/setdb.go`): clean match and the entry path before the
    climb. If the climb reaches the root without meeting match it returns
    `errMatchNotAncestor` instead of excluding every sibling of every
    ancestor; `updateRemovedBucket` passes it to `putDirs`, which answers
    400, so `MergeDirs` returns it wrapped in `ErrInvalidInput`. Only
    non-clean input reaches it: `bindPathsAndValidateSet` and `putDirs`
    don't clean paths, and `isDirentRemovedFromSet` matches the raw string
    prefix. The cycle-2 reviewer's probe showed that after `R/dir/` is
    removed, the entry `R/dir/../other/sub` matches `R/dir/`, and the climb
    then returns `errMatchNotAncestor`. So a direct PUT to the dirs endpoint
    with a `..` path reaches it, where origin/develop spins forever. 400 is
    right because the trigger is malformed client input, and every other
    `updateRemovedBucket` error in `putDirs` answers 400. The side effect is
    acceptable: `MergeDirEntries` has already stored the uncleaned dir,
    `removeChildEntriesFromRemovedBucket` finds no children for a `..`
    path, and the old code hung after the same writes. Skip a child only if
    it is the merged path or one of its ancestors (`childPath+"/"` prefix).
  - Tests (`server/server_test.go`): the two leaves also assert the dirs
    before (top) and after (top, top/dir/sub) the merge. They then
    rediscover and assert the files are exactly top/dir/sub/file, top/kept
