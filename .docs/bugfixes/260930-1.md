# Bugfixes 2026-09-30

Quality gates (run with iRODS auth active, the development wr manager v0.38.0
running, and IBACKUP_TEST_* env set; the Makefile exports CGO_ENABLED=1):

- `make lint`
- `make test`
- `make race`

- [x] `make lint` fails: gosec G703 "Path traversal via taint analysis" in
  `baton/baton_test.go` `pathWithoutBaton`.
  - Red: `make lint` exits 2 with
    `baton/baton_test.go:485:23: G703: Path traversal via taint analysis (gosec)`
  - Fixed in `baton/baton_test.go`: added a reasoned `//nolint:gosec`, matching
    existing test-code usage; the path comes from the test process's own PATH.
    No new test: behaviour is unchanged and lint is the check.
- [x] TestPuts hardlink race: two hardlinks to the same inode are handled by
  different put clients, which both upload the shared inode file
  concurrently; the second fails with CATALOG_ALREADY_HAS_ITEM_BY_THAT_NAME.
  The test's `waitForStatus("\nStatus: complete")` also matches
  "complete (but with failures".
  - Red: `CGO_ENABLED=1 go test -tags netgo --count 1 -run '^TestPuts$' .`
    (~4.5 min) failed 4/4 runs, including twice on the pre-update deps:
    `main_test.go:915 imeta ls -d failed for "<coll>/hardlink1": exit status 4;
    Dataobject <coll>/hardlink1 does not exist`. Set status detail showed the
    other hardlink `failed ... '<coll>/hardlinks/<tmp>/file/<inode>' error
    -809000 CATALOG_ALREADY_HAS_ITEM_BY_THAT_NAME`.
  - Fixed in `server/claims.go` (new), `server/server.go` and
    `server/setdb.go`: when reserving, a hardlink request claims its remote
    inode path; requests in the same client batch share the claim, and others
    are requeued with a wr queue dependency until the claim is released when
    the holder finishes, fails or is buried. A request's stale claim from an
    abandoned reservation (TTR expiry or retry release) is dropped first.
    Claim errors are logged and the request skipped.
  - Tests in `server/server_test.go`: hardlinks to one inode are not split
    across clients, including after a client holding both is abandoned.
    `main_test.go` now waits for "\nStatus: complete\n" so failures aren't
    treated as success.
- [x] TestWatchFofnsRealWRIntegration: watchfofns polls the correct watch dir
  but never submits a wr job, so the upload never appears.
  - Red: `CGO_ENABLED=1 go test -tags netgo --count 1 -run
    '^TestWatchFofnsRealWRIntegration$' .` (~40s) fails every run, including
    on the pre-update deps: main_test.go:5679 `waitForRemoteFile("<coll>/
    watchfofns_realwr/00/00/f000") failed: expected ils to succeed ... within
    20s; ... output=watchfofns: polling <tmp>/watchfofns_watch every 1s`.
    Raising the wait to 2m didn't help, and `wr status` showed no watchfofns
    jobs.
  - Fixed in `main_test.go`: the cause was in the test. watchfofns ran
    in-process, so its wr jobs (built from os.Executable()) ran the test
    binary, whose TestMain failed to build in the job's cwd yet exited 0, so
    wr saw instant success. The test now runs watchfofns as the built ibackup
    binary in a subprocess, waits up to 2m per remote file (nested collection
    creation is slow), and TestMain exits 1 when its self-build fails. No
    product change, so no new product test.
- [ ] Requests from different sets for the same local file map to the same
  remote data object and can be handed to different put clients at once, so
  the same concurrent-upload race as the hardlink bug could hit normal files.
  - Found while fixing the hardlink bug: applying the reservation claim to
    every request's RemoteDataPath broke existing server tests at
    server_test.go lines 1734, 2065 and 3633, which reserve such requests for
    separate clients concurrently.
  - Now seen failing a gate: `make race-main` TestPuts "Repeatedly uploading
    files that are changed or not changes status details" (main_test.go:3836),
    where sets changingFilesTest.v1-v3 share the same files and remote:
    `changingFilesTest.v3 ... Status: complete (but with failures - try a
    retry) ... file2 failed ... Failed to put data object: '<coll>/file2' error
    -818000 CAT_NO_ACCESS_PERMISSION`. Intermittent; passed in the earlier
    non-race `make test`.
  - Investigated: that failure was not this race. The v1-v3 sets run one
    after another, so no same-remote requests from different sets coexist in
    the queue there. iRODS experiments reproduced -818000 only when the object
    is removed during the put, and a concurrent test run's TestMain cleanup
    removed the whole shared collection during that window (see the
    test-isolation item below). The cross-set race is still possible in
    principle but has no failing gate; left unconfirmed for the user to
    decide.

- [x] Main-package TestMain cleanup (`resetIRODS`, main_test.go) runs
  `irm -rf` on the whole shared base IBACKUP_TEST_COLLECTION, so any
  main-package test run deletes the data of concurrent runs (or anyone else
  sharing the collection). This caused the CAT_NO_ACCESS_PERMISSION TestPuts
  failure in `make race-main`, and may explain the TestTrashRemove and TestSync
  failures above.
  - Red: `imkdir -p $IBACKUP_TEST_COLLECTION/other_run_probe; CGO_ENABLED=1 go
    test -tags netgo --count 1 -run '^TestNoServer$' .; ils
    $IBACKUP_TEST_COLLECTION/other_run_probe` -> the test passes (9.8s) and
    the probe collection is gone.
  - Fixed in `main_test.go` and `internal/testutil/irods.go`: removed the
    TestMain `resetIRODS` wipe (each test's unique subcollection is already
    removed by its t.Cleanup), made `resetIRODSOrFail` take the test's own
    collection explicitly, and removed the now-unused `NewIcommanderNoTB`. No
    automated test: process-level TestMain cleanup can't be exercised from
    inside the package; the probe check is the proof.
- [ ] Test collections leak when a test process is killed or times out
  (t.Cleanup doesn't run), and each Convey leaf creates its own collection,
  so one killed run can leave dozens of `ibackup_test_*` collections in the
  shared base. The old TestMain wipe hid this. Possible safe fix: in
  `RequireIRODSTestCollection`, remove only `ibackup_test_*` collections
  older than a cutoff far beyond the longest test run (e.g. 24h). Not a gate
  failure.
